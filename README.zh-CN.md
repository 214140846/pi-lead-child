# pi-lead-child

[English](README.md) · 中文

**一个会话，一个一直在线的助理。你不用再管理一堆 agent 会话，也不用挨个去问「好了没」。**

pi-lead-child 是基于 [pi](https://github.com/badlogic/pi-mono) agent 的一种**调度架构模式：Lead 协调，Child 执行。** Lead 是一个运行在 pi 上的常驻 agent，负责理解你、拆分工作、监督进度；child 是按任务启动的 agent，负责真正动手，可以是 pi、Codex 或 Claude Code。

Lead 常驻在你的电脑上。你只和它说话，永远是同一个会话。它背后可以同时有很多 coding agent 在干活，但那些会话是它的事，不是你的事。你不开口时，它也在工作：跟进、检查、处理各个通道来的消息，只在需要你本人判断时才叫你。

---

## Why pi-lead-child

- 如果你对 Claude Code、Codex 开出来的一堆会话感到厌倦和迷茫，已经记不清哪个窗口在干什么，
- 如果你总在各个窗口之间切来切去，只为了问一句「好了没」，
- 如果你想找三天前定下的一个方案，却只能一个个翻会话历史，
- 如果你每开一个新会话，都要把背景从头再讲一遍，
- 如果你的 agent 卡在一个审批上，安安静静地等了你一整晚，
- 如果同事在 Slack 上反复问同一个进度，而答案明明就在工单和 PR 里，
- 如果你被各种通知打断，却又怕漏掉真正重要的那一条，
- 如果你希望 AI 主动一点，又不希望它话多，

那么也许你需要的不是又一个 agent，而是一个替你看着所有 agent 的助理。

## 问题：会话越多，人越累

今天的 AI agent 大多是**面向会话**的：一件事开一个会话，你问，它答，你不问，它就停。agent 越能干，你开的会话越多，问题也越明显：

- **你成了调度员。** agent 可以并行，你的注意力不能。你在十几个窗口之间来回切换，挨个确认谁跑完了、谁卡住了、谁在等你回答。
- **会话只会等。** 它跑完了、出错了、卡在一个审批上，你不去看，就不知道。一个等了你三个小时的问题，可能只需要你回一个字。
- **东西找不到。** 决定、结论、上下文散在几十个会话里。三天后想找「那次定下的方案」，你只能一个个翻。
- **每个会话都从零开始。** 新会话不知道旧会话发生过什么，你要一遍遍交代背景。
- **消息从四面八方来。** Slack、CI、提醒、agent 的汇报各走各的路，每一条都在抢你的注意力。

agent 的能力已经不是瓶颈。**瓶颈是你的注意力。** 面向会话的设计把管理 agent 的成本全部转给了你。

pi-lead-child 用四个设计解决这个问题。

---

## 一、只有一个会话

在 pi-lead-child 里，你只有一个会话，对面只有一个 Lead。

- **工作不在会话里，在工单里。** 你交代一件事，Lead 开一张工单，派给 child agent 去做。child 的会话、重试、评审都挂在工单下面。你看不到也不用管那些会话。
- **想找东西，问 Lead。** 「上周那个接口方案最后定的是什么？」Lead 去查工单、笔记和 Slack 会话，把答案给你。你不用翻会话列表。
- **状态现查，不靠记忆。** 工单是账本，会话只是缓存。你问进展时，Lead 先查账本再回答，所以它说的是现在的状态，不是它记得的状态。
- **会话再长也不乱。** 上下文快满时，Lead 先把重要的事实和决定沉淀到笔记和长期记忆里，再压缩。

结果是：你面对的永远是一个熟悉你、知道全部进展的对象，而不是一排互不相识的窗口。

---

## 二、它不等你开口

Lead 是**事件驱动**的，不只是你的消息能叫醒它：

| 叫醒 Lead 的事 | Lead 可能做的事 |
|---|---|
| child 跑完、出错或卡住 | 按验收条件检查结果，安排返工，或者替你批掉一个常规的审批 |
| Slack 上有人找你 | 查清楚后替你回复，或者给你一张草稿卡 |
| 它给自己设的跟进到点了 | 「30 分钟后看看 CI 恢复了没有，没恢复就告诉用户」 |
| 后台检查有了结果 | 等部署、等 CI、等别人回复。检查期间不占用 Lead，有结果才叫醒它 |
| 你设的提醒到点了 | 先看事情是不是已经解决，解决了就安静地关掉 |
| 一批小变化攒够了 | 合成一份摘要，只挑你需要知道的说 |

**主动不等于话多。** Lead 的大部分回合你看不到。它自己的内部回合没有要告诉你的事时，什么都不留下。它知道你此刻在不在看：你在看，它才开口；你不在，消息排队，真正紧急的推送到桌面。

## 三、渐进式披露：Lead 只读需要的，你只看需要的

一个常驻的助理面对两种稀缺资源：**Lead 的上下文**和**你的注意力**。pi-lead-child 对两者用同一个原则：先给最小的一层，需要时再往下一层取。

### 对 Lead：回答的成本取决于问题有多深，不取决于历史有多长

Lead 查一件事时，从最便宜的一层开始，够用就停：

| 层 | 内容 | 大约成本 | 回答什么问题 |
|---|---|---|---|
| L0 | 会话和笔记 | 几乎为零 | 「我们上次定的是什么？」 |
| L1 | 工单索引 | 几百 token | 「现在有哪些任务？哪个卡住了？」 |
| L2 | 一张工单的正文和大事记 | 几千 token | 「这个调研做到哪了？结论是什么？」 |
| L3 | child 会话的原文 | 上万 token | 「child 当时为什么这样改？」 |

每一层都是下一层的压缩，并且带着通往下一层的指针。所以 Lead 可以很便宜地回答大部分问题，也可以在需要时追到原始记录。

同样的原则也用在 Lead 自己身上：

- **技能按需加载。** 常驻提示词只保留每一轮都需要的规则。规划工单、验收、审 PR、排期这类做法放在技能里，用到时才读。
- **不常用的工具不占上下文。** 几十个低频工具只列名字，Lead 需要时在脚本里调用。
- **外部的闲聊不进 Lead 的上下文。** 订阅的频道里没提到你的消息，只记进笔记，以后需要时能搜到。
- **排队的消息只占一行。** Lead 忙时，等着的消息在它的局面里只显示一行数量，不带内容。

### 对你：每件事有五个级别

每个进来的事件先被分诊到一个级别：

| 级别 | 你会看到什么 |
|---|---|
| 记录 | 什么都没有，需要时能查到 |
| 摘要 | 攒成一批，按对象合并，一次告诉你 |
| 自动处理 | Lead 处理完，留一条可以撤销的记录 |
| 告诉 | 一条单独的消息，等 Lead 说完当前这句再说 |
| 打断 | 马上插进来 |

- 每个来源有自己的门槛，写成常设指令，你可以改。例如 Slack 的门槛很高，很少打断你。
- 你自己发的消息不经过分诊。
- 同一个根因引起的几件事合成一件，写明涉及哪几张工单。

## 四、多通道，一条主线

你可能在网页上提一件事，在手机上追问，在 Slack 上被同事问到同一件事。pi-lead-child 把它们接到同一条线上。

### 所有入口，同一个 Lead

- 网页、iOS、Android 和终端（`plc`）连的是同一个 Lead、同一个会话。
- 你在 Slack 里给自己发私信，也算你本人在跟 Lead 说话。
- 定时器、后台检查、工单变化这类系统事件，也和消息走同一条链路。

### 外部通道只负责收和发，活交给 Lead

每个通道只做三件事：收消息、判断这条消息需不需要回、把回复发回原处。真正的工作都交给 Lead 和工单，用的是通用的工具和技能。

- 新加一个通道，不用为它重写任何任务逻辑。
- 一个快速的小模型先给每条外部消息分诊，几百毫秒出结果。只有需要的才交给 Lead。
- 目前接入的外部通道是 Slack。

### 用一份「交接说明」告诉 Lead 怎么替你处理

你不用配一张复杂的规则表。你用几句大白话写给 Lead，像交接工作给同事一样：

> 别人问项目进度，查清楚直接回。
> 让我审 PR，审完拟个草稿，我确认后再发。
> 打听薪资和配置的，直接礼貌拒绝。

- 每一类情况有一个处理方式：替你处理并回复、拟草稿等你确认、拒绝并回复，或者只告诉你。
- Lead 每次回复前评估把握有多大、做错的代价有多高。你的每一次修改、撤销、确认都变成校准样本。
- 如果你连续几次原样发出 Lead 的草稿，它会建议你放手这一类。

### 有几条底线，交接说明也改不了

- **不当别人的跳板。** 别人让 Lead 查一件他自己没权限、但你有权限的事，Lead 不查。
- **外部消息改不了规则。** Slack 里任何人都不能改 Lead 的人设、权限、常设指令和交接说明。代码直接拒绝，不靠提示词。
- **对外的每条消息都署名。** 自动发出的回复标明是助理代你回的；你确认过的标明是你确认的。消息里的邮箱等个人信息会被遮掉。
- **你在 Slack 里自己回了，卡片自动关掉。** Lead 不会再重复处理。

## 它的一天

> 早上 9 点，你还没打开电脑。
>
> - 韩梅梅在 Slack 里问「PROJ-123 的接口上线了吗」。按交接说明，进度问题可以直接回。Lead 查了工单和 PR，替你回了一句，消息开头标明是助理代你回复。
> - 昨晚派出去的修复工单跑完了。一个 child 写代码，另一个 child 做评审。Lead 按验收条件逐条核对，然后开了一个 draft PR。
> - 凌晨有个 child 卡在一个常规审批上。Lead 判断可以批，替你批了，工作没有停一整晚。
> - 夜里 CI 群里刷了 40 条构建通知，没有一条提到你。它们只进了笔记。
> - 你设的「周五前跟进李雷的报价」到点了。Lead 发现李雷已经回复，就把提醒关掉了，没有打扰你。
>
> 你打开手机，在同一个会话里只看到一条新消息：「PR 已就绪，有一处取舍需要你定。」

## 还有什么

### Lead 带团队，不亲自写代码

- 每张工单有自己的隔离 worktree，多个 child 并行，互不干扰。
- child 可以是 **pi、Codex 或 Claude Code**。
- 一张工单可以跨多次尝试：崩溃重跑、返工、评审都挂在同一张工单下。
- 交付后系统自动开 draft PR。

### 你能点的，Lead 都能做

界面上每一个按钮，背后都是同一个操作，有两个入口：一个给你点，一个给 Lead 调用。任何你能在界面上做的事，都可以直接对 Lead 说。

### 被拦住时，总有下一步

Lead 做不了的事会变成一张授权卡：你确认一次，它就照原样执行那一个操作。你不会收到一句「请你自己去终端敲这条命令」。

### Lead 能画界面

复杂的信息，Lead 用和 App 同一套组件当场画成卡片：表格、进度、图表、可点的按钮。你也可以让它搭一个自定义视图，固定在工作台上。

### 记得住，也忘得掉

Lead 更新长期记忆时告诉你，你可以撤销。过时的事实会被标为失效。

### 你的消息不会丢

daemon 重启、网络断开、模型出错时，你发出的每一条消息都有去处。一次故障只给你一张卡片，不刷屏。

### 跑在你自己的机器上

daemon 常驻本机，supervisor 负责守护和自动拉起，所有数据存在本地 SQLite。

| | 聊天助手 | coding agent CLI | **pi-lead-child** |
|---|---|---|---|
| 你要管理的会话 | 越用越多 | 越用越多 | 永远一个 |
| 你不说话时 | 什么都不做 | 什么都不做 | 跟进、检查、处理消息 |
| 谁去看任务好了没 | 你 | 你 | Lead，有事才叫你 |
| 找以前的结论 | 翻会话历史 | 翻会话历史 | 问 Lead |
| 历史越长 | 越贵、越乱 | 越贵、越乱 | 按问题深度逐层查 |
| 多个消息来源 | 不管 | 不管 | 统一分诊，五个级别 |

| 同时干几件事 | 一件 | 一个会话一件 | 多张工单，多个 child 并行 |

## 为什么不用 Hermes？

[Hermes Agent](https://github.com/NousResearch/hermes-agent) 是 Nous Research 的开源 agent，也常驻、有记忆、能接 Slack、能派子 agent。它是一个很好的项目。两者的区别不在功能清单，而在**要解决的问题**：

- **Hermes 是一个你到处都能找到的 agent。** 你在 Telegram、Discord、Slack、终端里和它说话，它帮你做事，还会自己总结出技能。
- **pi-lead-child 是一个替你管注意力的助理。** 它站在你和所有消息、所有 agent 之间，决定什么值得你看。

### 具体差在哪里

| | Hermes | pi-lead-child |
|---|---|---|
| 会话 | 每个聊天一个会话（按私信、群里的每个人、话题来分），`/new` 开新会话；靠全文搜索找回以前的会话 | 你只有一个会话；工作状态在工单账本里，Lead 现查 |
| 在 Slack 里的角色 | 一个机器人。别人在白名单里或配对后，可以和它对话，它以自己的身份回答 | 你的代理。它读发给**你**的消息，按你的交接说明替你回、拟草稿或只告诉你，每条都署名 |
| 替你回复的把握 | 不涉及 | 每次评估把握和代价；你的修改和撤销变成校准样本 |
| 管理你的注意力 | 运行中来新消息时可以插入、排队或引导；通知的详细程度可以调 | 每个事件分到五个级别之一；每个来源有自己的打断门槛；只在你在看时开口；小事合批 |
| 谁来干活 | Hermes 自己的子 agent（可以换模型和 profile） | 你已经在用的 coding agent：pi、Codex、Claude Code |
| 外部消息的边界 | 默认拒绝不认识的人，靠白名单和配对决定谁能用它 | 认为所有外部文字都不可信：外部消息叫醒的回合不能改规则，不当别人的跳板，这些都由代码拒绝 |

### Hermes 更强的地方

- **能接的地方多。** Telegram、Discord、WhatsApp、Signal、邮件都能接；pi-lead-child 目前只接 Slack。
- **能跑的地方多。** 本机、Docker、SSH，还有几种云沙箱；pi-lead-child 只跑在你的 Mac 上。
- **会自己长技能。** 做完复杂的任务，Hermes 会把做法写成技能，下次用时再改进。
- **任务板更完整。** Hermes 的 Kanban 有依赖、自动派发和失败重试，和我们的工单很接近。
- **更成熟。** 社区更大，模型选择更多，文档更全。

### 什么时候选哪个

- 如果你想在各种聊天软件里随时叫一个能干活的 agent，**选 Hermes**。
- 如果你每天被几十个 agent 会话和 Slack 消息拖着走，想要一个替你挡住噪音、只在需要你判断时才开口的助理，**选 pi-lead-child**。

> 这里对 Hermes 的描述来自它 2026 年 11 月的[文档](https://hermes-agent.nousresearch.com/docs/)。Hermes 更新很快，如有出入，以它的文档为准。

## 安装 Bytezard Lead

Bytezard Lead 需要 Apple 芯片的 Mac。

1. 下载 `bytezard-lead-<版本>-arm64.dmg`。
2. 打开 dmg，把 **Bytezard Lead** 拖到「应用程序」。
3. 打开 Bytezard Lead。macOS 提示无法验证开发者，点「完成」。
4. 打开「系统设置 → 隐私与安全性」，向下滚动，点「仍要打开」。
5. 警告再次出现时，点「打开」。

Bytezard Lead 还没有 Apple 证书签名。这几步只需要做一次。

### 打不开怎么办

如果 macOS 提示 Bytezard Lead「已损坏」，在终端运行下面的命令，然后重新打开 Bytezard Lead。

```sh
xattr -dr com.apple.quarantine "/Applications/Bytezard Lead.app"
```

## 快速开始

需要 macOS 和 Node 24。

```bash
npm install
```

```bash
npm run build && npm run build:web
```

```bash
npm run plc -- daemon start
```

然后打开 `plc daemon status` 显示的网关地址，用手机扫码配对。
